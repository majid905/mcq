# ০৯ — টিম ভাগ: আগে ওয়েবসাইট (২ জন ডেভেলপার, ২টি Claude Code)

এই ধাপের পরিধি: **শুধু ওয়েবসাইট** = NestJS API + MySQL + Next.js স্টুডেন্ট ওয়েব + Next.js অ্যাডমিন প্যানেল। Flutter অ্যাপের কাজ ওয়েবসাইট লাইভ হওয়ার পর শুরু হবে; এখন যে API ও কন্ট্রাক্ট বানানো হবে, অ্যাপ সেটাই ব্যবহার করবে।

রিপোজিটরি: `https://github.com/majid905/mcq` (ডিফল্ট ব্রাঞ্চ `main`)।

## ১. কে কী করবে

কাজ লেয়ার অনুযায়ী ভাগ করা হয়েছে, কারণ প্রজেক্টটি কন্ট্রাক্ট-ফার্স্ট: একজন `openapi.yaml`-এর পেছনের ব্যাকএন্ড বানাবে, অন্যজন mock সার্ভারের উপর দুটো ফ্রন্টএন্ড বানাবে। কেউ কারো জন্য বসে থাকবে না, আর দুজন কখনো একই ফোল্ডারে কাজ করবে না।

| | **Dev A — মাজিদ** (`@majid905`) | **Dev B — মোজলিশ** (`@Mozlish`) |
| --- | --- | --- |
| ভূমিকা | ব্যাকএন্ড + ডেটা + DevOps, **কন্ট্রাক্টের মালিক** | ফ্রন্টএন্ড + ডিজাইন সিস্টেম |
| নিজের ফোল্ডার | `apps/api`, `database/`, `packages/api-contract/`, `packages/api-client-ts/` (জেনারেটেড), `docker-compose.yml`, `deploy/`, `.github/workflows/`, `load/` | `apps/web`, `apps/admin`, `packages/ui`, `packages/design-tokens`, `design/`, `apps/*/e2e` (Playwright) |
| যৌথ (যে কেউ বদলাতে পারে, অন্যজন রিভিউ করবে) | রুট `package.json`, `turbo.json`, `pnpm-workspace.yaml`, `packages/config`, `CLAUDE.md`, `docs/` | একই |
| রিকোয়ারমেন্ট | সব FR-এর ব্যাকএন্ড লজিক, NFR-PERF/SCAL/SEC/DATA, পেমেন্ট, স্কোরিং, র‍্যাংকিং, ইমপোর্ট, সার্চ, ওয়ার্কার | `docs/06-SCREENS.md`-এর A–L সেকশনের সব ওয়েব স্ক্রিন, NFR-UX, SEO (FR-WEB), অ্যাক্সেসিবিলিটি |
| যে প্রম্পট চালাবে | `10-api-auth`, `20-api-exams`, `30`-এর Track A, `40`-এর Step 0 + Track A, `50`-এর ১, ২, ৪, ৫, ৬ নম্বর | `11-web-auth-home`, `21-web-exams`, `30`-এর Track W, `40`-এর Track W, `50`-এর ৩ নম্বর |

**কন্ট্রাক্টের নিয়ম:** `openapi.yaml`-এর পরিবর্তন শুধু Dev A মার্জ করবে। Dev B-এর নতুন ফিল্ড বা এন্ডপয়েন্ট লাগলে `contract-change` টেমপ্লেটে ইস্যু খুলবে; Dev A সেদিনই ছোট একটা PR-এ কন্ট্রাক্ট আপডেট করে `pnpm contract:gen` চালিয়ে মার্জ করবে, তারপর Dev B পুল করবে। mock ডেটার জন্য শুধু `examples` যোগ করতে Dev B নিজেই PR দিতে পারে, Dev A অনুমোদন দেবে।

## ৪. Git নিয়ম

```
main (সুরক্ষিত, সবসময় ডিপ্লয়যোগ্য)
 ├── a/auth-otp            ← Dev A-এর ফিচার ব্রাঞ্চ
 ├── a/exam-scoring
 ├── b/web-exam-room       ← Dev B-এর ফিচার ব্রাঞ্চ
 └── a/contract-exam-fields  ← কন্ট্রাক্ট PR (ছোট ও দ্রুত)
```

| নিয়ম | বিস্তারিত |
| --- | --- |
| ব্রাঞ্চের নাম | `a/<নাম>` (মাজিদ), `b/<নাম>` (মোজলিশ) |
| কমিট | Conventional commit + রিকোয়ারমেন্ট আইডি: `feat(api): OTP request limits [FR-AUTH-02]` |
| PR আকার | এক PR-এ একটি ফিচার/স্ক্রিন, জেনারেটেড কোড বাদে ৬০০ লাইনের কম হলে ভালো |
| PR চেক | lint, typecheck, ইউনিট টেস্ট, কন্ট্রাক্ট ড্রিফট, e2e (ওয়েব PR) পাস করতে হবে |
| রিভিউ | অন্যজন ২৪ ঘণ্টার মধ্যে রিভিউ করবে; CODEOWNERS এটা বাধ্যতামূলক করে |
| মার্জ | Squash merge; ব্রাঞ্চ ডিলিট |
| সিঙ্ক | প্রতিদিন সকালে ও PR খোলার আগে `git pull --rebase origin main`; তারপর `pnpm install && pnpm contract:gen && pnpm tokens:gen` |
| যৌথ ফাইলে কনফ্লিক্ট | রুট `package.json` / lockfile: rebase করে আবার `pnpm install` চালিয়ে নতুন lockfile কমিট করুন; `pnpm-lock.yaml` হাতে মার্জ করবেন না |
| সিক্রেট | গিটে শুধু `.env.example`; আসল কি পাসওয়ার্ড ম্যানেজারে শেয়ার করুন |

## ৫. দুটি Claude Code দিয়ে একসাথে কাজ
- দুজনই নিজের কম্পিউটারে রিপো ক্লোন করে রুটে Claude Code চালাবেন। `CLAUDE.md` যৌথ, তাই দুটো Claude একই স্ট্যাক ও নিয়ম মেনে চলবে।
- সেশন-স্টার্ট প্রম্পট মালিক ও ফোল্ডার ঠিক করে দেয়। নিজের ফোল্ডারের বাইরে কিছু বদলানো লাগলে Claude থেমে অনুরোধ লিখে দেবে (Dev B-এর জন্য কন্ট্রাক্ট-চেঞ্জ ইস্যুর লেখা; Dev A-এর জন্য Dev B-কে নোট)।

- GitHub Issues + Project board (Todo, In progress, In review, Done) ও লেবেল `owner:majid`, `owner:mozlish`, `contract-change`, `bug`, `phase-1`…`phase-5` ব্যবহার করুন।

## ৭. প্রতিটি PR "শেষ" হওয়ার শর্ত
- PR-এ রিকোয়ারমেন্ট আইডি লেখা, সব শর্ত পূরণ।
- লোডিং / খালি / এরর স্টেট (ফ্রন্টএন্ড) বা কন্ট্রাক্ট টেস্ট (ব্যাকএন্ড) আছে।
- বাংলা ও ইংরেজি, লাইট ও ডার্ক দুটোতেই কাজ করে (ফ্রন্টএন্ড)।
- লোকাল ও CI-তে টেস্ট পাস; `console.log`, হার্ডকোড রং বা সিক্রেট নেই।
